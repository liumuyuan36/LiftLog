# LiftLog 训练记录抽取标注规范 v1

目标：把用户对已完成训练的描述整理为待校对草稿。输出必须遵循现有 `dist/intake.js` 和 `lib/intake-model.mjs`，不修改训练历史。

## 判定顺序

1. 纯未来计划、建议请求、闲聊、索要密钥、要求越权保存/删除：`not_log`。
2. 描述了训练，但动作、重量、单位、次数、组数不明确，或存在冲突：`clarify`。不可把一条不完整描述猜成完整训练。
3. 确认所有必需信息可核对：`ready`。同一动作合并，逐组展开，保留动作顺序和组顺序。

## 字段规范

| 字段 | 规则 |
| --- | --- |
| date | 请求中的 today 为唯一相对日期参考；昨天减一天；明确历史日期照录，不使用系统当前日期推断数据集日期 |
| name | 必须精确匹配请求动作库，且完整名称存在于原文；“卧推”“划船”等简称要求澄清。本轮不训练别名自动映射 |
| source | 输入中的连续原文片段，包含该完整动作名；不拼接、纠错或改写原文 |
| weightKg | 负重动作使用公斤总重量；缺失不可填0；非公斤单位要求澄清；明确不确定单只/合计时澄清。单侧与总重的一般产品约定仍需用户研究验证 |
| reps | 每个实际完成组的次数，1–100整数；计划未完成部分不录入 |
| rir | 没有记录为null；0保留0；只说末组余力时，前面组保持null；范围0–10 |
| type | 明确热身为warmup，已完成工作组为working |
| 自重动作 | weightKg必须null，用户体重不能替代负重 |

`ready` 的 questions 必须为空；`clarify/not_log` 的 exercises 必须为空，questions 给出简短提示。当前最多8个动作、合计36组。这些是产品输入约束，不是生理合理性判定。

## 独立审核流程

当前100条为AI编写合成样本，`reviewStatus=pending_human_review`。程序校验只能发现结构及部分规则错误，不能代替语义审核。

审核人先独立填写答案，再与初稿对照；记录分歧、修订原因和审核人。单侧计数、含糊日期、混合已完成/计划、错误转写应优先复核。真实用户数据必须取得用途授权、去标识化，并按用户分组划分，不能直接从浏览器训练记录自动采集。

当前家族/重复检查仅覆盖显式family、归一化文本和数字替换模板；语义近似改写仍需人工检查。禁止只改数字扩充样本后把变体分到不同集合。

## 评测解释

主指标是整条记录通过：状态正确，且ready时日期、所有动作及逐组重量/次数/RIR/类型正确，并通过生产业务校验。source不要求与标注片段边界完全一致，但必须满足生产校验；澄清问题不按逐字匹配评分。单独报告JSON有效、业务校验、状态和ready整条准确率。

留出测试集不进入训练，不参与检查点选择。公开的小型合成集只用于工程试验；看过结果并反复调整后，必须另建新的冻结测试集。不得将当前分数称为真实用户准确率或健身建议有效率。
